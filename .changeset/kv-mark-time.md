A forget ledger whose reads lag, as Workers KV's, no longer misses a copy restored in the minute after its mark passed it, nor counts a restore twice when an older mark shows after it counted. Every value a mark keeps comes with the time it was raised: `ForgetLedger.readMark(name)` resolves `ForgetLedgerMark[]`, `{ value, raisedAt }` highest first (none for a mark never raised), `raiseMark(name, { value, raisedAt })` takes the time, and a new optional `pruneMarks(name, before)` removes the values raised before a time but the highest of them. A ledger whose reads show every write keeps the highest value with the time it was first raised, as the SQL ledgers, `durableObjectForgetLedger` and the memory ledger do, the SQL ones in a twelfth version of their scope, which reads a mark raised before as raised at the epoch; one with `visibilityDelayMs`, as `kvForgetLedger`, keeps every value with each time, a key of its own each. Each start raises the generation it read at the time it started, before the generation moves on, and the database keeps when the last restore was counted (`runtime:restore-covered`): a start counts at once a restore the marks its reads show tell, and once they show every mark raised before it started, a `visibilityDelayMs` later, counts one they tell that nothing counted, however far the generation moved since and whichever instance looks next; a mark raised before the latest restore counted tells no other. A restore counted while the reads did not show one counted a moment before, which took the same number, is counted past it then, recorded under the `restore:recounted` mark. A ledger of your own implements the new signatures; `forgetLedgerContract` checks both kinds.
