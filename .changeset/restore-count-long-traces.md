Restores are counted once on long runs of copies, crashes and declarations. A committed entry of the forget ledger the database lacks tells a restore only when written after the latest restore counted, on every ledger, not only one whose reads lag: one written by then is that restore's, however late the ledger shows it or takes it, so a forgetting whose write landed in the ledger after the restore that lost it was counted and reconciled no longer counts another, and one written after a restore counted that no reconciliation read through yet no longer passes as that restore's. The database keeps the time of the latest restore counted (`runtime:restore-covered`) on every ledger, a start that finds a restore counted in place keeps it at once, and `forget-ledger:reconciled` is gone. An instance tells a count another instance made while the ledger could not say the latest count, which took a number already counted, by that time, and no longer counts the same restore again; a copy that holds the same count, counted earlier, is a restore. A database holding fewer restores than the ledger counted since the latest restore it counted is a copy from before that count, a restore, though its generation took the same number; a count is raised to the ledger only once the database holds it, and a recount on a ledger whose reads lag tells the ledger it is one before it raises its count, and leaves the database where handling the last restore left it. On such a ledger, `app.restored()` made before the reads show every mark raised before the start, that would count nothing, waits until they do and counts the restore they tell.
