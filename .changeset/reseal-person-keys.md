Recover from a full compromise. A rotation rewrites how keys are wrapped, never the keys that seal the data, so a leak of the database, the tenant key store and the master key at once left every person's key, and the database's key, with whoever took them. `rotateTenantKey({ reseal: true })`, `bounda tenant-key rotate --reseal`, and the Durable Object's `rotateTenantKey` through `connect`, now puts a new version of the tenant's key in force and replaces every key that seals personal data: the worker replaces each person's key, in force or kept under a legal obligation, keeping the old one superseded in `bounda_superseded_keys` while it still opens something, and the database's key, keeping the old one as the previous. Once every instance has taken the new keys (`RESEAL_SWITCH_MS`), it seals again under them everything the store holds of persons, a batch per transaction that reads what it rewrites: events and process states, stored and scheduled commands, a redaction's kept values, dead letters and their error text layered under several persons, subscribers' last failures, remembered answers, layered or sealed at rest. A value under a key no store keeps any more, forgotten or redacted, becomes `null` under a key no one keeps. Snapshots go, every read model that holds personal data is rebuilt under the new keys, and, in one transaction, the scheduled commands and dead letters are read again and the old keys destroyed, their fingerprints kept so the forget ledger names them with the keys that replaced them and a copy restored from before the reseal forgets again whoever was forgotten since. The database's previous key goes once the last idempotency key filed under it expires. It runs with the app live, crash-safe and resumed where it stood; `status().keyRotation.reseal` and `bounda status` say the step under way, `rotateTenantKey` and `retireTenantKeys` are refused until the old keys are destroyed, and another reseal until it is complete. A rotation pass that cannot rewrap the tenant's key under the master key, or the database's key, now waits before it tries again, as one that cannot hold a person's key does.

For adapter authors: `PersonalKeyStore` gains `supersede`, `predecessors`, `countSuperseded` and `destroySuperseded`, `find` hands out a superseded key with its `successor`, and `remove`, `clear` and `kids` take superseded keys in; `IndexKeyStore` gains `previous`, `supersede` and `dropPrevious`, and `rewrap` reaches the previous key; `IdempotencyStore` gains `reseal`; `ReadModelRebuild.commit` takes `marks`, checkpoints set with the swap. Each read model's table records in its checkpoints which database key its blind indexes are computed under (`read-model:epoch:<name>`), so projections write under that key until a rebuild moves the table under the new one; `where` matches a sealed field under both keys meanwhile, through an operator only the runtime writes, `nin`, which both table engines take, and `client.blindIndexes(field, value)` gives a hand-written statement every index a value may have. The storage contracts cover all of it, and the restore contract reseals and restores a copy from before on every adapter.
