`bounda tenant-key rewrap-master` reaches every tenant key store the configuration can name. A configuration that is a function of the tenant may give tenants stores of their own; the command read only the store the starting tenant's configuration names, so it reported none left under a previous master key while other stores still held keys under it, and removing that key then would have made those tenants' personal data unreadable. It now reaches tenants as `forget-ledger prune --all-tenants` does: from `--tenant`, or `default`, the tenants each reached tenant's tenant key store and forget ledger list, and those the `tenants` export of `bounda.config.ts` names, until none is new, reading each store once, and rewraps each key under the key wrapper of its tenant's own configuration. A tenant whose configuration or stores cannot be read is named on standard error and the command exits with `2`, as one whose key could not be rewrapped is; the message for those reads `<tenant>'s key could not be rewrapped`. `rewrapTenantKeys` takes `config` as a `ProjectConfig`, with `tenant` and `tenants`, and resolves to `unreached` beside `rewrapped` and `left`, both in code-unit order. `listTenantsUnderPreviousMaster` keeps reading the one store a tenant's configuration names, with its own `ListTenantsUnderPreviousMasterArgs`; `UnreachedTenant` is exported as before. `listForgetLedgerTenants` now reads a database that holds both a forget ledger and tenant keys as both, where it read only the first it met.
