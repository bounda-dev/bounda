A forget ledger whose reads lag, as Workers KV's, is read once more `visibilityDelayMs` after a restore found while the app runs, as after a start: a forgetting committed in the minute before, which the restore lost and the first read did not show, is applied then rather than at the next start, which counted it as another restore; what that read applies of entries written before the restore was counted is that restore's. It also counts a restore that lost a committed forgetting the start's reads did not show yet, though a later forgetting of the same person, or the generation's moves since, left nothing else to tell it: a committed entry written since the latest restore counted (`runtime:restore-covered`) whose event the database lacks is a restore however the database stands, and a restore an adapter counted where it put the copy back moves that time too once a start takes it, as one found while running did, so the next start does not count it again. Reading its marks no longer costs more the longer an app runs: each start lets go of the values raised more than `visibilityDelayMs` before it but the highest, once it compared them and the ledger took the generation it read, so instances that never live past the delay no longer pile up keys, and an instance that compared every mark prunes once a `visibilityDelayMs` rather than with every raise. A mark then lists the values raised in the last few delays: one for each move of the generation and each start.
